# Уточнение: две роли и цикл доработки

## S107: источник и DL-107: решение

Пользователь в этом чате, 2026-10-10, сообщил о пропущенных двух ролях и
невозможности повторной подачи. В ответ на уточнение подтвердил направление:
«Организатор подаёт → согласующий возвращает → организатор исправляет и подаёт
повторно → согласующий решает». Это устраняет обратное направление ролей в
первоначальной формулировке. Источник прочитан, частный чат; авторитет — решение
пользователя. Фактический рабочий процесс независимо не исследован.

DL-107: добавить две роли и повторную подачу в утверждённый локальный прототип.
Критерий: возврат не должен оставлять заявку без следующего действия. Устраняет
часть G103 о доработке и меняет прежнее ограничение первого прототипа. Полная
история решений, отзыв согласования и настоящая авторизация остаются за границей.

## Спецификация и граница архитектуры

| Правило | Наблюдаемое поведение |
|---|---|
| RULE-008 | Организатор подаёт, исправляет и готовит; согласующий согласует или возвращает; действия другой роли недоступны |
| RULE-009 | Возвращённая заявка редактируется организатором и отправляется повторно как та же сущность, снова «На согласовании» |
| RULE-010 | Последний комментарий сохраняется при повторной подаче; подготовка ждёт нового согласования |

Роль выбирается кнопками «Организатор» / «Согласующий»; после загрузки —
организатор. Это локальная демонстрация, а не вход разных людей. Обе роли видят
состояние одной выбранной заявки. Контролы ограничены ролью; модель также
отклоняет неподходящего актора. Настоящих сетевых прав доступа эти проверки
не подтверждают.

| Действие | Организатор | Согласующий | Состояние |
|---|---|---|---|
| Подать заявку | Да | Нет | Новая |
| Согласовать / вернуть с комментарием | Нет | Да | На согласовании |
| Исправить и отправить повторно | Да | Нет | На доработке |
| Выполнить задачи | Да | Нет | Согласовано |
| Смотреть решение и готовность | Да | Да | Любое |

У организатора: поле «Исправленное название мероприятия» и кнопка «Отправить
повторно». Название обязано содержать текст; пустое/пробельное значение вызывает
ошибку без смены статуса. Успешная подача сохраняет id и список задач, меняет
название и статус. Последний комментарий остаётся как история, а не новое решение.
При новом возврате комментарий обновляется; полная история нескольких решений
пока не реализуется.

Подготовка недоступна для возвращённой и повторно поданной заявки до нового
согласования. Схема и ключ localStorage не меняются; прежние валидные заявки
должны читаться без потери данных. Это обратимое расширение локальной модели,
без миграции production-данных и без новых зависимостей.

## Сценарии и трассируемость

S107 → DL-107 → PROB-001 → RULE-008–010 → `event-application-roles.spec.ts`:

- Организатор не принимает решение; согласующий не подаёт и не выполняет задачи.
- Возврат с комментарием → исправление → повторная подача → новое согласование;
  id и число заявок прежние, комментарий виден, задачи ждут решения.
- После reload возвращённая заявка остаётся доступной для исправления.
- Пустое исправленное название не меняет статус.
- Во втором цикле правило обязательного комментария сохраняется.

Старые сценарии не отменяются: проверки переключают роль перед действиями,
сохраняя проверки статусов обеих сторон, комментария, задач и сохранения.
