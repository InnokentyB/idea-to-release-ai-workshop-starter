# Заявки и подготовка мероприятий — локальный прототип

Прототип на основе учебного шаблона воркшопа Иннокентия Бодрова и Андрея Буракова.
Позволяет подать заявку, согласовать или вернуть её с комментарием, затем
выполнить обязательные задачи и увидеть готовность мероприятия.

Данные сохраняются в localStorage текущего браузера под ключом
`event-applications-v1`. Общего сервера данных и входа отдельных пользователей нет.
Переключатель «Организатор» / «Согласующий» демонстрирует две роли: организатор
подаёт, исправляет и готовит; согласующий принимает решение. Действия другой
роли недоступны. Возвращённую заявку организатор исправляет и отправляет повторно,
сохраняя её идентификатор и последний комментарий. Четыре задачи временные.

При входе и после перезагрузки открывается реестр «Все заявки»: поиск по названию,
фильтры этапов, решения, оставшиеся задачи и готовность. Согласующий в реестре
начинает с очереди «На согласовании». Действие строки открывает выбранную заявку;
«Вернуться к списку» возвращает обзор. Создание открывается явно. На узком экране
каждый элемент списка показывает все поля отдельным блоком.

Проверка текущего продукта:

```bash
npm run test:e2e
```

## Методология TDPD

Проект использует Test-Driven Product Development (TDPD), авторскую методологию
Иннокентия Бодрова. Правила для Codex находятся в `AGENTS.md`, установленный
фреймворк и шаблоны — в `.tdpd/`, исходный репозиторий — в Git submodule
`methodology/tdpd`, закреплённом на `workshop-v0.3.1`.

После клонирования и при получении изменений с подключённым фреймворком:

```bash
git submodule update --init --recursive
node methodology/tdpd/bin/tdpd.js status --target .
node methodology/tdpd/bin/tdpd.js audit --target .
```

Контекст подключения и открытые вопросы: `.tdpd/project-context.md`.
Продуктовые артефакты заявок на мероприятия: [docs/tdpd/event-applications](docs/tdpd/event-applications/README.md).
Для продуктовых изменений применяется полный маршрут: источники и контекст,
проблема, спецификация, сценарии, e2e RED, реализация до GREEN, ручная приёмка
(UAT). Успешный аудит установки не означает прохождение продуктовых этапов.

## Отдельный учебный пример чек-листа

Сценарии ниже относятся к исходному примеру в `workshop/` и checkpoint-веткам.
Они сохранены отдельно от нового продукта заявок.

- **S1:** создать событие с названием и будущей датой;
- **S2:** добавить задачу и отметить её выполненной;
- **S3:** увидеть понятные сообщения для пустой задачи, пустых полей события и даты в прошлом;
- **S4:** сохранить событие и задачи после обновления страницы.

Проверка сценариев:

```bash
npm run test:e2e:workshop
```

На текущей реализации заявок и учебной ветке `checkpoint/red` эти проверки
ожидаемо падают: они требуют отдельный интерфейс учебного чек-листа.
В основной `test:e2e` они не включены, их содержание не изменено.

## Контрольные точки

```bash
npm run checkpoint -- list
npm run checkpoint -- go red
npm run checkpoint -- go slice-1
npm run checkpoint -- go slice-2
npm run checkpoint -- go green
```

Команда `go` сначала сохраняет незавершённые изменения в `git stash`, затем переключает контрольную ветку. Чтобы вернуть сохранённые изменения:

```bash
npm run checkpoint -- recover
```

Маршрут не использует `git reset --hard` и не удаляет файлы участника.

## Публикация

Первая выкатка на **вайбхостинг.рф**: [подготовка, проверки и открытые блокеры](docs/tdpd/event-applications/deployment.md).
Корневые `Dockerfile` и `llmdevops.yaml` подготовлены для stateless HTTP на 8080
с `/health`. Ручной workflow **Prepare VibeHosting image** проверяет production
сборку и публикует образ в GHCR; сам хостинг подключён через MCP.

Проверка пользовательских сценариев на production-сервере:

```bash
npm run build
npx playwright test --config playwright.release.config.ts --workers=2
```

Статический маршрут:

- build command: `npm run build`;
- output directory: `dist`.

Web service или контейнерный маршрут:

- build command: `npm run build`;
- start command: `npm run start`;
- health check: `/health`;
- port: переменная окружения `PORT`.
